# ALMAS · Arquitectura causal del contrato preencarnatorio v2

## 1. Principio

El contrato preencarnatorio no se identifica con el origen de las almas.

`ORIGEN` responde **de dónde proceden o cómo se relacionan ontológicamente**.

`CONTRATO` responde **qué finalidad, papel, prueba o integración se habría asumido antes de encarnar**.

Puede existir, dentro de los modelos comparados:

- contrato sin origen compartido;
- continuidad kármica sin contrato bilateral demostrable;
- origen compartido sin cláusulas contractuales reconstruibles;
- misión individual sin contrato romántico;
- vínculo significativo sin contrato preencarnatorio evaluable.

## 2. Cadena contractual canónica

La reconstrucción FULL del contrato utiliza:

`TAREA_PREVIA → MOTIVO_DE_ELECCION_DEL_OTRO → ROL_ASUMIDO → CLAUSULA_DE_ACTIVACION → PRUEBA_PACTADA → INTEGRACION_ESPERADA → CONDICION_DE_CUMPLIMIENTO → FORMAS_DE_CIERRE_O_ALTERNATIVA`

### C1 · TAREA_PREVIA

¿Qué trae cada alma antes del encuentro?

Debe existir en la arquitectura individual con la carta del otro retirada.

Salida separada:

- `TAREA_A_PREVIA`
- `TAREA_B_PREVIA`

### C2 · MOTIVO_DE_ELECCIÓN_DEL_OTRO

¿Por qué el otro es un activador adecuado de esa tarea?

Cadena:

`TAREA_PREVIA_RECEPTOR → FACTOR_DEL_OTRO → ENCAJE_GEOMETRICO → RECURRENCIA → CAUSA_CONTRACTUAL`

No significa necesariamente que la doctrina utilizada enseñe una elección mutua literal.

### C3 · ROL_ASUMIDO

¿Qué función desempeña cada alma?

Direcciones:

- A_EN_B;
- B_EN_A;
- CAMPO_COMUN.

El rol es funcional, no identidad esencial.

### C4 · CLÁUSULA DE ACTIVACIÓN

¿Qué debe poner en movimiento el encuentro?

No describe el resultado final. Describe la función que debe volverse activa.

Ejemplos funcionales:

- reconocimiento;
- vulnerabilidad;
- autonomía;
- verdad;
- transformación;
- encarnación.

### C5 · PRUEBA PACTADA

¿Qué tensión debe atravesarse para que exista aprendizaje?

La prueba se formula como polaridad o problema operativo:

`PRINCIPIO_A ↔ PRINCIPIO_B`

Ejemplos:

- cercanía ↔ autonomía;
- ideal ↔ realidad;
- reconocimiento ↔ reciprocidad;
- poder ↔ entrega;
- silencio ↔ verdad.

Una dificultad observada no se convierte automáticamente en “prueba pactada”; debe rastrearse hasta tarea previa + activador + cláusula.

### C6 · INTEGRACIÓN ESPERADA

¿Qué capacidad nueva debería poder coexistir después del proceso?

Formato:

`antes: principios escindidos → después: coexistencia funcional`.

La integración es función, no desenlace romántico.

### C7 · CONDICIÓN DE CUMPLIMIENTO

¿Qué cambio observable indicaría que la cláusula ya no necesita expresarse de la misma forma?

Debe definirse **antes** de evaluar el hecho usado como cumplimiento.

Requiere:

- firma funcional;
- hechos posteriores;
- comparación antes/después;
- contraevidencia;
- seguimiento suficiente.

### C8 · FORMAS DE CIERRE O ALTERNATIVA

¿Qué modalidades son compatibles con que la función contractual se transforme o cierre?

Pueden incluir:

- encarnación conjunta;
- redefinición;
- servicio;
- transformación de modalidad;
- liberación;
- cierre;
- ruta alternativa;
- función no integrada / aplazada.

Ninguna modalidad se deduce automáticamente de una fecha futura.

## 3. Niveles de resolución contractual

### R0 · NO_EVALUABLE
No existe base suficiente.

### R1 · TEMA_PREENCARNATORIO
Puede sostenerse una tarea, prueba o misión previa general.

Kardec 258–259 es un ejemplo doctrinal de elección del **género** de prueba sin elección necesaria de cada detalle.

### R2 · FUNCION_RELACIONAL_PREENCARNATORIA
Puede reconstruirse que una relación específica encaja como activadora de tareas previas.

Esto es una operacionalización ALMAS.

### R3 · MODELO_DE_ACUERDO_BILATERAL
La arquitectura es compatible con que ambas partes desempeñen roles complementarios dentro de un modelo doctrinal o método que contemple acuerdo previo.

No equivale a demostrar históricamente una conversación pre-natal literal.

### R4 · CONTENIDO_LITERAL
Frases, promesas, fechas, matrimonio, reunión obligatoria o detalles concretos supuestamente acordados.

**No puede alcanzar SUPPORTED desde astrología.** Por defecto: `NOT_EVALUABLE`.

## 4. Granularidad

Toda inferencia contractual indica:

- `THEME` — tema o género de prueba;
- `FUNCTION` — función relacional;
- `ROLE` — rol de una persona respecto de otra;
- `CONDITION` — condición general de activación/integración;
- `EVENT` — acontecimiento concreto;
- `DETAIL` — detalle literal.

La fuerza inferencial disminuye al pasar de THEME/FUNCTION a EVENT/DETAIL.

Astrología temporal puede corroborar EVENT como activación documental, pero no convertirlo retrospectivamente en detalle literalmente pactado.

## 5. Relación con las fuentes

### Kardec
Permite distinguir **género de prueba** de hechos secundarios y libre albedrío. Informa R1 y la regla de granularidad.

### Kardec · misiones
Permite un modelo de misión solicitada antes de encarnar. No implica contrato bilateral.

### Luria/Vital
Aporta motivos de retorno, tikkun, ayuda a otros y zivug dentro de su sistema específico.

### Swedenborg
Aporta un modelo providencial de pareja y reconocimiento, no reencarnacional.

### Myss
Aporta un método contemporáneo explícito de contrato sagrado y compromisos pre-natales.

### Newton / Wambach / Whitton / Schwartz
Aportan modelos identificados de intervida y planificación prenatal; no se tratan como demostración independiente.

### Kwilecki
Documenta académicamente la construcción New Age del soul contract como plan prenatal orientado al crecimiento.

## 6. Mapeo con motores existentes

La arquitectura v2 **no elimina** los motores diferenciales existentes.

| Cadena v2 | Motor existente |
|---|---|
| C1 TAREA_PREVIA | INDIVIDUAL_TASKS |
| C2 MOTIVO_ELECCIÓN | AGREEMENT_MOTIVE + CAUSA_CONTRACTUAL |
| C3 ROL_ASUMIDO | ROLE_SELECTION |
| C4 CLÁUSULA_ACTIVACIÓN | CLAUSE_ASSEMBLY + ENCOUNTER_CONDITIONS |
| C5 PRUEBA_PACTADA | nuevo ensamblaje causal sobre tareas/cláusulas |
| C6 INTEGRACIÓN_ESPERADA | CLAUSE_ASSEMBLY.integration_requirement |
| C7 CUMPLIMIENTO | FULFILLMENT_MECHANISMS |
| C8 CIERRE/ALTERNATIVA | FULFILLMENT_MECHANISMS |

`ORIGIN` se ejecuta antes como contexto ontológico, pero no forma parte de la cadena causal mínima del contrato.

`COMMON_TASK` alimenta C4–C8 como función emergente del campo común.

## 7. Gate anti-circularidad

Una cadena contractual es inválida si:

1. la tarea previa desaparece al retirar la carta del otro;
2. el motivo se inventa después de ver la cláusula;
3. el rol se deriva únicamente de una etiqueta narrativa;
4. la prueba sólo existe porque ocurrió un evento posterior;
5. la integración se define después de conocer el desenlace;
6. el cierre se infiere sólo por ausencia de contacto;
7. el origen se usa para rellenar automáticamente el contrato.

## 8. Trazabilidad

Toda cláusula contractual debe poder reconstruirse hacia atrás:

`cumplimiento → integración → prueba → activación → rol → motivo/causa → tarea previa`.

Si falla un eslabón, el estado máximo es `COMPATIBLE` o `INSUFFICIENT` según gravedad.

## 9. Narrativa

La narrativa se genera sólo después de cerrar la cadena.

La redacción puede adoptar forma de “contrato” hermenéutico, pero debe conservar un `contract_text_trace` que vincule cada frase a C1–C8.

## 10. Regla final

ALMAS reconstruye **funciones contractuales posibles**, no una transcripción literal de palabras pronunciadas antes del nacimiento.
